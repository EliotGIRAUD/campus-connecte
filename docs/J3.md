# J3 — Sécuriser et fiabiliser le système IoT

**Responsable :** toi.  
**Périmètre :** fiabilité du flux MQTT, validation, fraîcheur, pannes, secrets, observabilité (Grafana + Loki).  
**Hors périmètre J3 :** auth JWT, QR, commandes ventilation (journée ultérieure).

## Situation

Le prototype fonctionne dans le cas nominal. Il faut vérifier qu’il reste cohérent quand les données sont incorrectes, qu’un capteur disparaît ou qu’un composant tombe en panne — et **prouver** ces comportements via des logs centralisés.

## Questions à résoudre

1. **Comment distinguer sans ambiguïté plusieurs capteurs simulés qui publient en parallèle ?**  
   Identité stable `device_id` (`sensor-001` … `003`) dans le **topic** MQTT `campus/v1/devices/{device_id}/…`, le payload, PostgreSQL (`Device.id`) et l’API. Les logs portent `deviceId` + `eventId` (`message_id`).

2. **Quelles données entrantes doivent être refusées avant d’atteindre le cœur du système ?**  
   JSON illisible, schéma Zod invalide (champ manquant / type faux / valeur non finie), `device_id` ≠ segment du topic, objet hors registre. Événement : `telemetry.rejected` (+ `reason`).

3. **Comment détecter qu’un capteur ne fournit plus une information suffisamment fraîche ?**  
   `freshness = fresh|stale` si `now - observed_at < FRESHNESS_MS` (10 s). Distinct de `availability` (online/offline via LWT). Un capteur en `pause` reste online mais passe `stale`.

4. **Comment le système se comporte-t-il lorsqu’un message est dupliqué, retardé ou invalide ?**  
   Doublon (`message_id` unique) → `telemetry.duplicate`, pas de 2ᵉ ligne métier. Retard → stocké en historique, `telemetry.stale_kept`, `Device` non régressé. Invalide → rejeté, pas de crash.

5. **Que se passe-t-il si le broker MQTT devient indisponible puis revient ?**  
   Backend : `mqtt.disconnected` / `mqtt.error` puis `mqtt.reconnecting` et `mqtt.connected` (reconnectPeriod 2 s). Simulateur suspend / reprend. Messages en transit peuvent être perdus ; session `clean: true` = pas de file côté backend.

6. **Quels secrets et paramètres ne doivent jamais être versionnés dans Git ?**  
   Mots de passe MQTT non pédagogiques, `DATABASE_URL` de prod, secrets Grafana réels. Le dépôt contient `.env.example` (valeurs démo) ; `.env` local est ignoré.

## Fin de journée

### Fonctionne

- Logs JSON structurés (`eventType`, `deviceId`, `eventId`, …) + stack Grafana/Loki/Promtail dans Compose.
- 11 scénarios obligatoires exécutés avec preuves (API + LogQL + logs Docker).
- Validation Zod, dédup, retard, fraîcheur, ACL + cohérence topic déjà en place et re-prouvés.

### Incomplet ou en échec

- Comparaison QoS 0 vs 1 **pendant** une coupure : les publications échouent côté client si le broker est down ; on a prouvé la livraison à chaud des deux QoS + la reconnexion (pas un compteur « perdus QoS0 vs QoS1 » exhaustif).
- Démo visuelle Grafana à confirmer sur le poste (Explore + dashboard provisionné).

### Limites ou dette connue

- Session MQTT `clean: true` : pas de reprise des messages publiés pendant l’absence du backend.
- Compte `teacher` peut publier sur tous les topics (kit pédagogique).
- Auth / commandes hors J3.
- Promtail ne scrape que `backend` (choix volontaire pour tenir Loki en local).
