# J3 — Associer un objet et agir

**Responsable :** toi (après J2).  
**Prérequis :** cache hors ligne et règles doublon/retard de J2 en place. Ne pas commencer les alertes J4 ici.

## Situation

Un utilisateur scanne un équipement et demande l’activation de la ventilation.

## Questions à résoudre (à répondre en fin de J3)

1. Comment sait-on à quel objet on s’adresse et qui a le droit d’agir ?
2. Quelle différence entre une commande acceptée et une action réalisée ?
3. Que faire si la caméra est refusée ou si l’objet ne répond jamais ?

## Déjà en place

- Contrat MQTT commandes / résultats : `infra/docs/contrat-mqtt.md`
- QR du kit : `infra/docs/association.md` (`campus-device:v1:sensor-001`, etc.)
- État ventilation MQTT (`state`) déjà ingéré sur `Device.ventilation`
- Compte MQTT `backend` peut **publier** sur `campus/v1/devices/+/commands`
- Hors ligne : **ne pas rejouer** une commande à la reconnexion (consigne du sujet)

## Travail

### Backend

1. **Utilisateurs démo** (à hasher, pas en clair dans le dépôt) :
   - `lecteur` / `lecteur-demo` → lecture seule
   - `operateur` / `operateur-demo` → lecture + commande
2. **JWT** : `POST /api/auth/login`, middleware sur l’API métier. Un `lecteur` qui appelle `POST /api/devices/:id/commands` reçoit **403** (R11 : masquer le bouton ne suffit pas).
3. **Association QR** : `POST /api/associate` `{ code, room_id? }`
   - format invalide → 400 (`ceci-n-est-pas-un-objet`)
   - objet inconnu → 404 (`campus-device:v1:sensor-999`)
   - objet connu → mise à jour du **registre backend** (`Device.roomId`), pas du simulateur
4. **Commande ventilation** : `POST /api/devices/:deviceId/commands` `{ enabled: true|false }`
   - publier QoS 1, **sans retained**, `command_id` unique, `expires_at` (~15 s)
   - table `Command` : `pending` → `executed` | `rejected` | `timeout`
   - corréler le topic `results` ; un accusé MQTT seul **n’est pas** une preuve d’exécution
5. **Timeout** : pas d’attente infinie. Réponse tardive après timeout : journaliser, **ne pas afficher « activé »** ; documenter le comportement.
6. Si MQTT est down à l’émission → 503, commande en échec explicite.

Paramètres : `COMMAND_TIMEOUT_MS=15000`, `JWT_SECRET` pédagogique dans `.env.example`.

### Mobile

1. **Session** : écran de connexion ; jeton dans `expo-secure-store` (pas AsyncStorage pour le secret).
2. **Scan** : `expo-camera`, contenus du kit. Refus caméra : message + reprise (saisie manuelle du texte QR acceptable).
3. **Commande** : états UI **en attente / confirmé / échec ou inconnu**. Jamais « activé » sans `status === executed`.
4. **Hors ligne** : bouton ventilation bloqué + explication, aucune file silencieuse.

Incidents kit : `tools command sensor-001 on` (diagnostic), `incident sensor-001 no-response` / `respond`.

## Jalons

| Jalon | Preuve |
|---|---|
| Scan associe l’objet attendu | QR valide + registre API |
| Sans droit → refus même en appelant l’API | login `lecteur` + POST commande → 403 |
| Résultat ventilation confirmé par le système | `executed` + évolution CO₂ / `state` |
| Absence de réponse compréhensible | `no-response` → timeout, pas « activé » |

Recettes : **R08, R09, R10, R11**.
