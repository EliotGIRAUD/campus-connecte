# J3 — Sécuriser et fiabiliser le système IoT

**Responsable :** toi.  
**Périmètre :** fiabilité du flux MQTT, validation, fraîcheur, pannes, secrets, observabilité (Grafana + Loki).  
**Hors périmètre J3 :** auth JWT, QR, commandes ventilation (J4), alertes et gel (J5).

## Situation

Le prototype fonctionne dans le cas nominal. Il faut vérifier qu’il reste cohérent quand les données sont incorrectes, qu’un capteur disparaît ou qu’un composant tombe en panne — et **prouver** ces comportements via des logs centralisés.

## Questions à résoudre

1. **Comment distinguer sans ambiguïté plusieurs capteurs simulés qui publient en parallèle ?**  
   Identité stable `device_id` (`sensor-001` … `003`) dans le **topic** MQTT `campus/v1/devices/{device_id}/…`, le payload, PostgreSQL (`Device.id`) et l’API. Les logs portent `deviceId` + `eventId` (`message_id`).

2. **Quelles données entrantes doivent être refusées avant d’atteindre le cœur du système ?**  
   JSON illisible, schéma Zod invalide (champ manquant / type faux / valeur non finie), `device_id` ≠ segment du topic, objet hors registre. Événement : `telemetry.rejected` (+ `reason`).

3. **Comment détecter qu’un capteur ne fournit plus une information suffisamment fraîche ?**  
   `freshness = fresh|stale` si `now - observed_at < FRESHNESS_MS` (10 s). Distinct de `availability` (online/offline via LWT). Un capteur en `pause` reste online mais passe `stale`.

4. **Comment le système se comporte-t-il lorsqu’un message est dupliqué, retardé ou invalide ?**  
   Doublon (`message_id` unique) → `telemetry.duplicate`, pas de 2ᵉ ligne métier. Retard → stocké en historique, `telemetry.stale_kept`, `Device` non régressé. Invalide → rejeté, pas de crash.

5. **Que se passe-t-il si le broker MQTT devient indisponible puis revient ?**  
   Backend : `mqtt.disconnected` / `mqtt.error` puis `mqtt.reconnecting` et `mqtt.connected` (reconnectPeriod 2 s). Simulateur suspend / reprend. Messages en transit peuvent être perdus ; session `clean: true` = pas de file côté backend.

6. **Quels secrets et paramètres ne doivent jamais être versionnés dans Git ?**  
   Mots de passe MQTT non pédagogiques, `DATABASE_URL` de prod, secrets Grafana réels. Le dépôt contient `.env.example` (valeurs démo) ; `.env` local est ignoré.

### 1. Validation métier : message valide ≠ mesure valide

#### Comportement observé (avant correction)

| Injection | Résultat |
|---|---|
| `-300 °C`, `99999 ppm`, JSON valide, `observed_at` ≈ now | `telemetry.ingested` ; ligne `Measurement` créée ; devient brièvement le latest puis est écrasée par le simulateur |
| `observed_at = 2099-01-01` | Devient le **latest** ; `age_ms` **négatif** ; `freshness: fresh` ; le simulateur ne peut plus faire avancer le latest (`shouldUpdateLatest` refuse tout `observed_at` réel) |

Preuve :

```bash
# Absurde (rejouable)
docker compose exec -T mosquitto mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/devices/sensor-001/telemetry' -q 1 \
  -m '{"schema_version":1,"message_id":"inv1-absurd-now-001","device_id":"sensor-001","room_id":"salle-203","observed_at":"'"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"'","temperature":{"value":-300,"unit":"°C"},"co2":{"value":99999,"unit":"ppm"}}'
curl -s 'http://localhost:3000/api/devices/sensor-001?limit=5'
# chercher message_id inv1-absurd-now-001 dans measurements

# Futur (rejouable — attention : verrouille le latest tant que non corrigé / reset)
docker compose exec -T mosquitto mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/devices/sensor-001/telemetry' -q 1 \
  -m '{"schema_version":1,"message_id":"inv1-future-001","device_id":"sensor-001","room_id":"salle-203","observed_at":"2099-01-01T00:00:00.000Z","temperature":{"value":22,"unit":"°C"},"co2":{"value":800,"unit":"ppm"}}'
curl -s http://localhost:3000/api/devices/sensor-001
# latest.observed_at=2099… age_ms<0 freshness=fresh
```

#### Cause comprise

- **Contrat** (Zod) : nombre fini + unités — pas de bornes physiques, pas de garde sur le futur.
- **Fraîcheur** : `now - observed_at < FRESHNESS_MS` → un timestamp futur donne un âge négatif ⇒ toujours `fresh`.
- **Latest** : `incoming >= current` ⇒ le futur gagne et **bloque** les mesures normales.

Différence des validations :

| Niveau | Question | Avant |
|---|---|---|
| Contrat | Le JSON respecte-t-il le schéma kit ? | Oui (Zod) |
| Technique | Topic / device / dédup OK ? | Oui |
| Métier | La mesure est-elle crédible ? | **Non vérifié** |

Place architecturale : après parse contrat + identité, **avant** insert PostgreSQL (le lake peut garder le brut).

#### Risque / conséquence

État courant et historique empoisonnés ; démo « fraîcheur » mensongère ; capteur simulé silencieux côté UI jusqu’à reset manuel.

#### Décision : **corriger**

Bornes température / CO₂ + rejet `observed_at` trop dans le futur (tolérance 60 s). Voir ADR 009.

**Après correction (reprouvable) :** `reason=out_of_range` et `reason=observed_at_in_future` ; le latest du simulateur reste `fresh` (plus de verrouillage 2099).

### 2. `room_id` du message vs registre backend

#### Comportement observé

Publication `sensor-001` (catalogue `salle-203`) avec `room_id=salle-666` :

| Couche | Valeur |
|---|---|
| `GET /api/rooms` | Toujours sous **salle-203** |
| `Device.roomId` (Postgres) | **salle-203** (inchangé) |
| `Measurement.roomId` | **salle-666** (copié du payload) |
| `GET …/history` → `room_id` | **salle-203** (lu depuis `Device`) |

Preuve :

```bash
docker compose exec -T mosquitto mosquitto_pub -h localhost -u teacher -P teacher-demo \
  -t 'campus/v1/devices/sensor-001/telemetry' -q 1 \
  -m '{"schema_version":1,"message_id":"inv2-room-666-001","device_id":"sensor-001","room_id":"salle-666","observed_at":"'"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"'","temperature":{"value":25,"unit":"°C"},"co2":{"value":900,"unit":"ppm"}}'
curl -s http://localhost:3000/api/rooms   # sensor-001 reste salle-203
docker compose exec -T postgres psql -U campus -d campus \
  -c "SELECT \"messageId\", \"roomId\" FROM \"Measurement\" WHERE \"messageId\"='inv2-room-666-001';"
```

#### Cause comprise

Le seed / upsert catalogue fixe `Device.roomId`. L’ingestion copie `message.room_id` dans `Measurement` / averages, **sans** mettre à jour le device et **sans** comparer au registre.

#### Risque / conséquence

API produit cohérente (registre), mais historique SQL / moyennes peuvent porter une salle fantôme — confusion en audit, mauvais regroupements si on agrégeait sur `Measurement.roomId`.

#### Décision : **documenter + corriger légèrement**

- **Fait foi :** registre backend (`Device.roomId`).
- **Payload `room_id` :** conservé au contrat pour audit / kit ; log `telemetry.room_mismatch` si ≠ registre ; écritures métier avec le `roomId` du registre.

**Après correction :** `Measurement.roomId = salle-203` même si le payload dit `salle-666` ; log `telemetry.room_mismatch`.

### 3. Désordre réel et traitements concurrents

#### Comportement observé / analysé

- Le test `tools incident … delay` prouve le cas **séquentiel** : B après A avec `observed_at` plus ancien → `telemetry.stale_kept`, latest intact.
- Il **ne prouve pas** A∥B : deux handlers peuvent lire le **même** `lastObservedAt`, tous deux passer `shouldUpdateLatest`, et le **dernier `UPDATE` gagnant** peut être le message le plus ancien.

Preuve modèle (reproductible sans broker) :

```bash
cd backend && npm test
# sous-test « concurrence latest (modele) » dans concurrency.model.test.ts
```

#### Cause comprise

Pattern read → decide → write sans précondition SQL sur `lastObservedAt`. Un seul process Node limite la fenêtre, mais `handleMqttMessage` est `async` : deux messages peuvent s’entrelacer.

#### Risque / conséquence

Sous charge ou plusieurs workers : régression silencieuse du latest ; le test delay reste vert.

#### Décision : **corriger** (update conditionnel) + **documenter** la limite multi-workers

`UPDATE … WHERE lastObservedAt IS NULL OR lastObservedAt <= $incoming` ; `count = 0` ⇒ traiter comme non-régression (`stale_kept`).

Le scénario delay kit reste la preuve pédagogique séquentielle ; le modèle + l’update atomique couvrent la concurrence.

**Après correction :** `prisma.device.updateMany` conditionnel dans `ingest.ts` ; preuve modèle toujours dans `npm test`.
