# J4 — Rendre le produit exploitable

**Responsable :** collègue (après J3).  
**Prérequis :** J2 (données fiables) et J3 (QR + commandes) démontrés. Gel fonctionnel en fin de J4.

## Situation

Plusieurs salles émettent des mesures. Une règle doit signaler une anomalie sans créer une alerte à chaque message MQTT.

## Questions à résoudre (à répondre en fin de J4)

1. Faut-il conserver et afficher toutes les mesures ?
2. Comment éviter de créer une nouvelle alerte à chaque message ?
3. Comment identifier le composant en cause quand l’écran ne se met plus à jour ?

## Déjà en place

- 3 salles / 3 objets (`sensor-001` … `003`)
- Historique borné (J2) et `HISTORY_LIMIT=200`
- Paramètre prévu : `ALERT_CO2_PPM=1500`, hysteresis 200 ppm (ouvrir ≥ 1500, fermer ≤ 1300)
- Incidents kit : `high-co2` / `normal-co2` sur `sensor-001`

## Travail

1. **Règle d’alerte documentée** : une alerte ouverte par objet / type ; pas de nouvelle ligne à chaque télémétrie tant qu’elle est ouverte ; retour à la normale sous le seuil moins l’hysteresis.
2. **UI** : pastille ou liste d’alertes lisible (contraste du thème sombre, libellés masculins génériques).
3. **Tester les 3 salles** dans l’app.
4. **Traces** : une mesure et une commande doivent être retrouvables dans les logs backend (`message_id`, `command_id`).
5. **R07** : `docker compose stop mosquitto` puis relance — backend se reconnecte ; le mobile ne présente pas d’anciennes mesures comme fraîches.
6. **R02** : `incident sensor-001 invalid` — service disponible, pas de mesure normale, log de rejet.
7. **Lisibilité / erreurs** : parcours principal, états vide / erreur / hors ligne.
8. **README** : prérequis, Compose, adresses (dont IP LAN pour le téléphone), comptes démo, limites, version du kit `852f1b1`.
9. Dossier court si le sujet le demande : sécurité pédagogique (JWT démo, MQTT local, pas de secret réel).
