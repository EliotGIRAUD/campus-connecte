# J4 — Commander un objet et confirmer l’exécution

**Responsable :** collègue (après J3).  
**Prérequis :** J2 (données fiables) et J3 (validation, pannes, Grafana + Loki) démontrés.  
**Périmètre :** contrat de commande, topics MQTT commande/ACK, cycle de vie, timeout, idempotence, UI d’attente/confirmation.  
**Hors périmètre J4 :** règle d’alerte métier, README final, gel avant soutenance (J5).

## Situation

Depuis son téléphone, un utilisateur demande l’activation de la ventilation. Le système doit distinguer la demande envoyée de l’action réellement exécutée par l’objet.

## Questions à résoudre

1. Quelle différence entre une commande acceptée par le backend, publiée sur MQTT, reçue par l’objet et réellement exécutée ?
2. Comment rattacher la réponse de l’objet à la bonne commande ?
3. Que doit faire le système si l’objet est hors ligne, si l’ACK est perdu ou s’il arrive après le timeout ?
4. Que se passe-t-il si la même commande est reçue deux fois ?

## Capsules

2. **L’incertitude d’un système distribué :** timeout, réponse tardive, doublon et idempotence.

## Jalons

| Jalon | Statut | Preuve |
|---|---|---|
| Commande téléphone → objet via backend + MQTT | réussi | `command.accepted` → `command.sent` + topic commands |
| ACK `commandId` rattaché | réussi | `command.acknowledged` + `GET` status `ACKNOWLEDGED` |
| Mobile attente / confirmée / échouée / expirée | réussi | UI `RoomDetail` + libellés `commandStatusLabel` |
| Absence d’ACK → timeout | réussi | `COMMAND_TIMEOUT_MS` + incident `no-response` ou objet stoppé |
| Parcours reconstruisible via `commandId` | réussi | LogQL `|= "COMMAND_ID"` |
| Rejeu sans double effet silencieux | réussi | 2ᵉ POST même `command_id` → 200 + `command.duplicate_request` ; 2ᵉ ACK → `command.ack_duplicate` |
| Équipe explique ce que le système sait | réussi | tableau ci-dessous + ADR 011 |

### Ce que le système sait à chaque étape

| État | Connaissance réelle |
|---|---|
| `PENDING` | Acceptée en base ; pas encore (ou pas encore confirmé) publiée |
| `SENT` | Publiée sur MQTT ; **pas** de preuve d’exécution |
| `ACKNOWLEDGED` | Objet a publié `executed` pour ce `command_id` |
| `FAILED` | Objet a rejeté, ou publish MQTT impossible |
| `TIMEOUT` | Aucun ACK avant `expires_at` ; exécution **incertaine** |

## Preuves reproductibles

Prérequis : `docker compose up -d` (stack healthy).

### 1. Flux nominal (mobile / curl → ACK)

```powershell
$body = '{"action":"set_ventilation","enabled":true}'
$cmd = curl.exe -s -X POST http://localhost:3000/api/devices/sensor-001/commands `
  -H "Content-Type: application/json" -d $body | ConvertFrom-Json
$cmd.command_id
$cmd.status   # SENT puis, après ~1 s :
Start-Sleep -Seconds 2
curl.exe -s "http://localhost:3000/api/devices/sensor-001/commands/$($cmd.command_id)"
# status ACKNOWLEDGED, result.status executed
```

LogQL :

```logql
{compose_service="backend"} |= "<command_id>"
```

Attendu : `command.accepted` → `command.sent` → (lake/queue) → `command.acknowledged`.

### 2. Timeout (objet silencieux / hors ligne)

```powershell
# Option A — incident kit (ignore les commandes)
docker compose --profile tools run --rm tools incident sensor-001 no-response

# Option B — arrêter le simulateur
# docker compose stop simulator

$env:COMMAND_TIMEOUT_MS="5000"   # optionnel: rebuild backend avec timeout court
$body = '{"action":"set_ventilation","enabled":false,"command_id":"j4-timeout-demo-1"}'
curl.exe -s -X POST http://localhost:3000/api/devices/sensor-001/commands `
  -H "Content-Type: application/json" -d $body
# attendre > COMMAND_TIMEOUT_MS
curl.exe -s http://localhost:3000/api/devices/sensor-001/commands/j4-timeout-demo-1
# status TIMEOUT ; logs command.timeout
```

Remettre : `tools incident sensor-001 reset` ou `docker compose start simulator`.

### 3. Commande dupliquée (idempotence API)

```powershell
$body = '{"action":"set_ventilation","enabled":true,"command_id":"j4-dup-demo-1"}'
curl.exe -s -X POST http://localhost:3000/api/devices/sensor-001/commands -H "Content-Type: application/json" -d $body
curl.exe -s -o - -w "%{http_code}" -X POST http://localhost:3000/api/devices/sensor-001/commands -H "Content-Type: application/json" -d $body
# 2e appel : HTTP 200 + même commande ; log command.duplicate_request
```

### 4. ACK après timeout

Après un `TIMEOUT`, republier manuellement un résultat (compte teacher) avec le même `command_id` :

```powershell
docker compose exec -T mosquitto mosquitto_pub -h localhost -u teacher -P teacher-demo `
  -t campus/v1/devices/sensor-001/results -q 1 `
  -m '{"schema_version":1,"device_id":"sensor-001","command_id":"j4-timeout-demo-1","status":"executed","executed_at":"2026-10-07T12:00:00.000Z","ventilation":false}'
# logs : command.ack_late ; GET status reste TIMEOUT ; late_ack_at renseigne
```

## Fin de journée

### Réponses aux questions

1. **Acceptée** = persistée `PENDING` ; **publiée** = MQTT `SENT` ; **reçue** = côté objet (invisible sauf ACK) ; **exécutée** = résultat `executed` → `ACKNOWLEDGED`. Seul le dernier prouve l’effet métier.
2. Corrélation par **`command_id`** identique dans la commande et le message `…/results`.
3. Objet hors ligne / ACK perdu → `TIMEOUT`. ACK tardif → `command.ack_late`, résultat stocké, **statut reste `TIMEOUT`**.
4. Même `command_id` + même contenu → réponse idempotente (pas de 2ᵉ publication). ACK répété → ignoré (`command.ack_duplicate`). Même id + contenu différent → HTTP 409.

### Fonctionne

- Cycle de vie complet API ↔ MQTT ↔ simulateur ↔ ACK.
- Timeout balayé chaque seconde.
- Mobile : états d’attente / confirmée / échouée / expirée.
- Preuves filtrables sur `commandId` (Loki).

### Incomplet ou en échec

- Rien de bloquant pour les jalons J4. Tag Git `J4` à créer après commit / présentation.

### Limites ou dette connue

- Pas de file de commandes pendant absence de l’objet (sessions clean du kit).
- Workers consolidation : latence ACK de l’ordre du poll (`CONSOLIDATION_POLL_MS`) — observé ~150 ms en local.
- Idempotence durable côté simulateur limitée au cache mémoire (kit).
- Pas d’auth utilisateur sur `POST /commands` (hors J4).

| Scénario | Résultat |
