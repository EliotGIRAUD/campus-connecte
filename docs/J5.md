## Preuves reproductibles

Prérequis : `docker compose up -d --build --wait`.

### 1. Alerte CO₂ (sans spam)

```powershell
# Avant
curl.exe -s http://localhost:3000/api/alerts?status=OPEN

docker compose --profile tools run --rm tools incident sensor-001 high-co2
Start-Sleep -Seconds 5
curl.exe -s http://localhost:3000/api/alerts?status=OPEN
# → exactement 1 alerte OPEN pour sensor-001, type high_co2

# Attendre encore des télémétries « hautes » puis revérifier : toujours 1 seule OPEN
Start-Sleep -Seconds 8
curl.exe -s "http://localhost:3000/api/devices/sensor-001/alerts?limit=5"
# → une OPEN (éventuellement peak_co2 mis à jour), pas N lignes OPEN

docker compose --profile tools run --rm tools incident sensor-001 normal-co2
Start-Sleep -Seconds 5
curl.exe -s http://localhost:3000/api/alerts?status=OPEN
# → liste vide
curl.exe -s "http://localhost:3000/api/alerts?status=RESOLVED&limit=5"
# → alerte RESOLVED avec resolved_co2 ≤ 1300
```

LogQL :

```logql
{compose_service="backend"} | json | eventType =~ "alert.*"
```

### 2. Suivi mesure + commande

```powershell
# Mesure : prendre un message_id depuis GET rooms
curl.exe -s http://localhost:3000/api/rooms

# Commande
$body = '{"action":"set_ventilation","enabled":true}'
$cmd = curl.exe -s -X POST http://localhost:3000/api/devices/sensor-002/commands `
  -H "Content-Type: application/json" -d $body | ConvertFrom-Json
$cmd.command_id
```

LogQL : `{compose_service="backend"} |= "<message_id_ou_command_id>"`

### 3. Multi-salles + historique borné

```powershell
curl.exe -s http://localhost:3000/api/rooms
# 3 salles salle-203/204/205
curl.exe -s "http://localhost:3000/api/devices/sensor-001/history" | ConvertFrom-Json |
  Select-Object -ExpandProperty measurements | Measure-Object
# ≤ HISTORY_LIMIT (200)
```

## Fin de journée

### Réponses aux questions

1. **Non, pas toutes.** On conserve un **historique brut borné** (`HISTORY_LIMIT=200` par objet, purge `history.trimmed`) pour l’affichage « live », plus des **moyennes 10 min / 30 jours** pour les graphiques longs. Le lake Mongo garde le brut MQTT 7 jours (audit), pas pour l’UI.
2. **Une alerte ouverte par objet et type** avec **hystérésis** : ouverture ≥ 1500 ppm, fermeture ≤ 1300 ppm. Tant que l’alerte est `OPEN`, les télémétries suivantes mettent éventuellement à jour `peakCo2` mais **ne créent pas** de nouvelle ligne (index unique partiel + `decideCo2Alert`).
3. **Séparer les couches** : NetInfo / bandeau téléphone ; `GET /health` (Postgres, Mongo, MQTT, lag consolidation) ; Grafana/Loki filtrés par `eventType` / `deviceId` / `commandId` / `alertId` ; disponibilité MQTT (`availability` + LWT) vs fraîcheur mesure. Un écran figé n’est pas forcément « MQTT mort » — vérifier d’abord le réseau téléphone, puis l’API `/health`, puis les logs backend.

### Fonctionne

- Règle d’alerte CO₂ serveur + API + UI mobile.
- Incidents kit `high-co2` / `normal-co2` pour ouvrir / résoudre.
- Multi-salles (3 devices) et historique borné inchangés.
- Commandes J4 + traces `message_id` / `commandId` / `alertId`.
- Tests unitaires hystérésis + format mobile.

### Incomplet ou en échec

- Pas de notifications push / WebSocket pour les alertes (polling rooms 3 s).
- Pas d’auth API (inchangé).
- Pas d’autres types d’alerte (température, objet offline prolongé) — hors énoncé J5 CO₂.

### Limites ou dette connue / écarts au périmètre

- Clean session MQTT côté objets : pertes possibles si backend down longtemps (déjà documenté J3/J4).
- L’indice mobile « CO₂ élevé » (seuil 1500 local) n’est **pas** l’alerte produit ; seule `active_alert` l’est (fermeture à 1300).
- Auth / QR restent hors produit livré.
